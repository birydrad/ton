# Броадкасты в TON

## Оверлей

Оверлей — это группа участников, которые могут отправлять друг другу сообщения
и броадкасты. Проще всего объяснить это на примерах.

Сейчас есть два типа оверлеев:

- **Публичный оверлей.** В него может вступить кто угодно. Через него
  распространяются external messages — сообщения, которые мы хотим выполнить в
  блокчейне, а также сами блоки. Соответственно, любой желающий может поднять
  ноду, подключиться к публичному оверлею и получать через него блоки.
  Особенность публичного оверлея в том, что в нём нет полного списка всех
  участников: каждый участник знает только нескольких соседей.

- **Приватный оверлей.** Например, группа текущих валидаторов. Их список
  известен и фиксирован, поэтому они могут использовать другой класс
  алгоритмов.

## Текущее устройство броадкастов

Сосредоточимся на публичных броадкастах.

В публичных оверлеях поддерживается список примерно из 20 пиров. Для текущей
задачи можно считать, что это случайные 20 пиров из всего состава оверлея. Из
этих 20 пиров мы выбираем 5 соседей. Для простоты пока тоже можно считать, что
они выбраны случайно.

Как разослать маленькое сообщение всем участникам оверлея? Отправим его всем
нашим соседям. Соседи при **первом** получении сообщения разошлют его своим
соседям, те — своим, и так далее. Если граф связный и все ноды активны, что
является довольно смелым допущением, сообщение в итоге доставится всем
участникам оверлея.

Так мы сейчас поступаем, если сообщение не больше 768 байт, то есть помещается
в один UDP-пакет вместе со всеми заголовками. Сообщение отправляется один раз,
ненадёжно, по UDP.

Что делать, если сообщение больше? Сейчас используется следующий исторически
сложившийся алгоритм:

1. Применяем forward error correction (FEC), а именно RaptorQ. На вход он
   получает сообщение, а на выходе даёт `2 * N` кусочков размером 768 байт.
   Любых `N` кусочков достаточно, чтобы восстановить исходное сообщение, где
   `N ~= payload_size / 768`.
2. Каждый кусочек броадкастится при помощи алгоритма для маленьких сообщений:
   каждые `freq` секунд мы отправляем очередной кусочек всем 5 соседям. Сейчас
   ограничения подобраны так, чтобы один броадкаст отправлял не больше
   примерно 5 MB/s.
3. Как только узел собирает `N` кусочков, он восстанавливает исходное
   сообщение. После этого он также может восстановить остальные `2 * N`
   кусочков и начинает броадкастить их дальше.

У такого подхода есть плюсы: мы просто шлём UDP-пакеты с определённой
скоростью и почти ни о чём другом не думаем. Например, не нужно отдельно
обрабатывать потери отдельных пакетов.

## Проблемы текущего подхода

Основных проблем две.

Первая — примерно `10x` трафика по сравнению с размером передаваемых данных.
Каждый узел рассылает `2 * N` пакетов пяти соседям, то есть `10 * N` пакетов.
При этом само исходное сообщение по размеру соответствует примерно `N` таким
пакетам.

Вторая проблема — ненадёжность при появлении большого числа нод, которые по
каким-то причинам не хотят рассылать пакеты дальше.

Сразу заметим очевидное узкое место: каждый пакет отправляется одним и тем же
5 соседям. Соответственно, все пакеты идут по фиксированному графу. Если этот
граф не связен, никакой FEC не поможет: часть узлов броадкаст не получит.

## Задача

В приложении лежит файл `broadcast-graph.json` с графом оверлея. Граф построен
на основе реального оверлея и является направленным: ребро `A -> B` означает,
что узел `A` знает узел `B` как соседа и может отправить ему сообщение.
Часть узлов заранее помечена как `leech`: это участники, которые плохо
участвуют в рассылке.

Формат файла простой:

- `nodes` — список узлов с числовым `id`;
- `node.leech` — `true`, если узел считается плохо ведущим себя участником;
- `edges` — список направленных рёбер;
- `edge.from` и `edge.to` — числовые `id` узлов;
- `edge.latency_ms` — примерная one-way задержка доставки по ребру в
  миллисекундах.

Требуется предложить улучшение публичных броадкастов.

Нам важны три параметра:

- скорость доставки;
- overhead по трафику;
- надёжность, в том числе поведение при наличии нод, которые плохо себя ведут.

Скорее всего, алгоритмы, которые лучше всего подходят для коротких сообщений
размером около 256 B и для длинных сообщений размером около 1 MB, будут
разными. На маленьких броадкастах значительную часть трафика могут занимать
служебные сообщения.

Поэтому в рамках этого задания мы считаем, что броадкастим сообщения размером
1 MB.

Другое ограничение: пока считаем граф фиксированным. Настоящий броадкаст,
скорее всего, должен выбирать в соседи хорошо работающие ноды.

Ожидается, что будет проведено небольшое исследование подходов. Эти подходы
нужно сравнить на выданном графе при помощи небольшого эмулятора.

Ожидается, что кандидат сам выберет разумные метрики, явно опишет допущения
модели и объяснит, почему предложенный алгоритм лучше текущего.

# Исследование

## Шаг 1. Теоретический floor по latency

Граф `broadcast-graph.json`: **1618 нод** (1124 honest, 494 leech), 24 370 directed edges,
out-degree ~20, edge.latency median 16 ms, max 144 ms.

**Модель** — store-and-forward + pipelined FEC streaming. Для receiver R:

```
T_decode(R) = min_{s in sources} Σ_edges_on_path(s→R) (latency_e + part_size / bw) + (K − 1) × part_size / bw
                                  ↑                                                   ↑
                          первая part пробегает path через H hops          ещё K−1 parts на bottleneck output rate
```

То есть это [Σ link-latency + Σ per-hop transmission] для первой part'и из ближайшего
source'а, плюс pipeline tail для остальных K−1 частей через bottleneck.

**Параметры.** Bandwidth `bw = 100 MB/s` на каждом ребре (uniform). Relay только через
honest. Destination = honest receivers. Multi-source = N случайных honest sources,
receiver видит min по всем sources.

**Body presets:**

- 100 KB body: K=25 parts × 4 KB. Transmission/hop = 0.04 ms.
- 1 MB body:   K=30 parts × ~35 KB. Transmission/hop = 0.33 ms.

**Код.** `test/broadcast-sim/graph_latency_floor.py` (Python, **отдельно** от bench-sim).
Запуск:

```
python3 test/broadcast-sim/graph_latency_floor.py broadcast-graph.json 1,10,23,100,400 30
```

**Результаты.** Для одного source — median по 100 seeds (формат `median (min..max, σ)`), для
multi-source — mean по 30/5 seeds (variance мизерный):

**1 source (100 seeds, full distribution)**

| body  | p50 | p90 | p95 | p99 | max |
|-------|-----|-----|-----|-----|-----|
| 100KB | 32 (26..148, σ=26) | 90 (85..200, σ=24) | 98 (91..213, σ=26) | 106 (100..222, σ=26) | 152 (137..270, σ=26) |
| 1MB   | 42 (36..158, σ=26) | 100 (94..210, σ=24) | 107 (101..222, σ=26) | 116 (110..232, σ=26) | 162 (147..281, σ=26) |

Distribution **right-skewed** — mean выше median т.к. неудачный выбор source-на-periphery
ставит p95 до 200+ ms. Для бенчмарка реальных алгоритмов важно усреднять по многим source picks.

**Multi-source (mean across seeds)**

100 KB:

| sources | p50 | p90 | p95 | p99 | max | unreached |
|---------|-----|-----|-----|-----|-----|-----------|
| 10  | 22 | 79 | 87 | 97 | 142 | 3 |
| 23  | 20 | 74 | 84 | 94 | 138 | 3 |
| 100 | 14 | 60 | 75 | 87 | 126 | 2–3 |
| 400 | 9  | 43 | 61 | 80 | 100 | 1–2 |

1 MB:

| sources | p50 | p90 | p95 | p99 | max | unreached |
|---------|-----|-----|-----|-----|-----|-----------|
| 10  | 32 | 88 | 97 | 106 | 152 | 3 |
| 23  | 29 | 84 | 93 | 103 | 148 | 3 |
| 100 | 23 | 71 | 85 | 96  | 135 | 2–3 |
| 400 | 18 | 54 | 70 | 89  | 109 | 1–2 |

Разница 100 KB → 1 MB по latency ≈ `(K−1)·part_size/bw + H·part_size/bw` (pipeline tail
+ per-hop transmission). 100 KB: ~1 ms добавки. 1 MB: ~10 ms.

**3 honest-ноды стабильно unreachable** через honest-only relay (их inbound edges идут
только через leech) → reach floor = **99.73 %**.

Этот floor используем как baseline для оценки реальных алгоритмов — насколько они близки
к оптимуму shortest-path для соответствующего числа senders.

## Шаг 2. Twostep-FEC на private overlay

Матрица пингов `L[i][j] = 3.554 + 0.008963·haversine_km` (fit public-overlay), fallback
50 ms. Geo из `overlay-peers.sim.json` (1263/1618 нод с lat/lon).

**Протокол** (упрощённый `overlay/broadcast-twostep.cpp`, FEC, но делегаты только honest):
source `S` генерирует `H−1` RaptorQ-символов (`H` = #honest), `K_needed = (H−1)/2`
достаточно для декода. Символ `i` адресуется делегату `D_i ∈ honest \ {S}`; делегат,
получив свой кусок от S, рассылает его всем остальным пирам.

Время прихода куска `i` у honest receiver R: `L[S][R]+tx` если `D_i = R`,
`L[S][D_i] + L[D_i][R] + 2·tx` иначе. Decode = `K_needed`-й по возрастанию arrival;
multi-source = min по `M` источникам.

**Трафик ≈ 2× body на узел.** Source шлёт `(H−1)·part ≈ 2·body`. Делегат пересылает
свой кусок остальным `N−2` пирам — тоже `~2·body`. Близко к информационному минимуму 1×.

**Код.** `test/broadcast-sim/twostep_floor.py` (numpy). Результаты (ms, body 100 KB/1 MB
неотличимы, tx negligible):

| sources | p50  | p90  | p95  | p99  | max  |
|--------:|-----:|-----:|-----:|-----:|-----:|
| 1       | 69.4 | 142.1| 144.5| 154.6| 208.8|
| 10      | 17.0 |  92.7|  94.2| 103.8| 158.3|
| 100     | 15.9 |  92.3|  93.9| 103.6| 158.0|
| 400     | 15.8 |  92.2|  94.5| 103.3| 157.9|

Reach 100 %. `K_needed=561` ≪ honest-arrivals.

**Вывод.** На 1 source twostep-FEC уже сравним с floor по p50 (69 vs 32 ms), но p95
хуже (144 vs 98) — 2-hop структура добавляет ~50 ms на дальние пары. **Multi-source с
M≥10 догоняет floor**: p50=17 ms vs floor 22 ms на 10 источниках, p95=94 vs 87.
Трафик 2× — почти оптимально.

## Шаг 3. Текущий production-FEC (fixed K5 + 5 MB/s)

`prod-fec-fixed-K5-5MB` (`overlay/broadcast/algorithms/fec.cpp`): RaptorQ 768 B, overhead
2.0×, источник на каждый piece шлёт K=5 **стабильным** соседям (salt=broadcast_id),
pacing **5 MB/s**. Setup: mainnet 1120 honest, leech=0%, 16324 рёбер, mean-degree 14.6.

| body  | sources | reach  |  p50 |  p90 |  p95 |
|-------|--------:|-------:|-----:|-----:|-----:|
| 100KB | 1       | 96.8 % | 101  | 159  | 171  |
| 100KB | 400     | 97.5 % |  34  |  90  |  99  |
| 1MB   | 1       | 96.8 % | 281  | 340  | 351  |
| 1MB   | 400     | 97.5 % | 214  | 271  | 280  |

Трафик: honest_x **12.8×**, p95_in **26.5×**, duplicate **90 %**.

**Две основные проблемы:**

1. **Фиксированный подграф** (stable_per_piece=true). Один salt на весь broadcast →
   каждый получатель форвардит на одну и ту же K=5 случайную подвыборку соседей. Reach
   стопорится на ~97 % — есть «карманы» куда K=5-фанаут не доходит, и они одинаковые
   для всех источников.

2. **Pacing 5 MB/s** ограничивает propagation для крупных body. Для 1 MB это даёт floor
   `1 MB / 5 MB/s = 200 ms` поверх сетевой задержки. p50=281 ms против 101 ms на 100 KB
   — разница ~180 ms = pacing.

## Шаг 5. K=10 — увеличение fanout не помогает на большом body

Попробовали `prod-fec-random-K10-inf` (то же что в Шаге 4, но K=10 random peers per piece).

| body  | sources | reach  |  p50 |  p95 | honest_x |
|-------|--------:|-------:|-----:|-----:|---------:|
| 100KB | 1       | 99.7 % |  74  | 140  | **25.9×**|
| 100KB | 400     | 99.7 % |  22  |  77  | 25.9×    |
| 1MB   | 1       | 99.7 % | 196  | 262  | 25.9×    |
| 1MB   | 400     | 99.7 % | 142  | 195  | 25.9×    |

vs Шаг 4 (K=5 random):

| body  |  K=5 p50 single |  K=10 p50 single | Δ        |
|-------|----------------:|-----------------:|----------|
| 100KB |              84 |               74 | **−12 %**|
| 1MB   |             149 |              196 | **+31 %**|

Трафик **×2 (13.2 → 25.9×)**.

**Вывод.** На малом body K=10 быстрее (больше параллельных путей). На большом body —
**медленнее**, потому что каждый relay тратит upload-канал на 2× больше копий → время
отправки (`body × K / bw_up`) становится bottleneck. К тому же overhead удвоился ни за
что: reach улучшилось всего на 0.3 pp (99.4 → 99.7).

**Random gossip — не та дорога**: чтобы уйти от random K=5, нужно учитывать latency и
топологию (geo-aware fanout, spanning tree, plumtree). Дальше — Шаг 6.

## Шаг 6. Plumtree (push/pull duality) с eager-cap

Без FEC два двойственных подхода: **push** («шлю всем, PRUNE при duplicate») и **pull**
(«молчу, REQUEST по HAVE»). Оба сходятся к одной структуре — у каждого узла часть рёбер
**eager** (по ним сразу летит body), остальные **lazy** (только HAVE). Plumtree это
явно реализует с persistent mesh в Shared (iroh-gossip): стартуют все eager, PRUNE-on-
duplicate демотит, GRAFT-on-timeout возвращает.

Добавил `eager_cap_min/max` в `PlumtreeConfig` чтобы ограничить размер mesh.

### Setup
mainnet 1120 honest (leech=0), 20 sources × 20 rounds × warmup=10. Один broadcast/round,
SessionState persists. Кандидаты: `pull-K=10`, `plumtree` (без cap), `plumtree-cap={5,10}`,
`subscribe-prune`, `prod-fec-random-inf` как baseline.

На 1 MB plumtree сжимается до 1.0× (как tree), но p50=229 — FEC-chunks у prod-fec
параллелятся и режут до 184. Plumtree-cap не помогает (cap'ы тяжелее uncapped по
latency без выигрыша по traffic).

В same-source режиме **plumtree uncapped — победитель**: 1.1× traffic (почти optimal
tree) + p50=110 ms (на 7-8 ms лучше cap=10 и prod-fec). Mesh быстро сходится к
fastest-path spanning-tree из этого источника, и дальше каждый broadcast идёт по
готовому дереву.

S's eager не схлопывается напрямую (S не получает duplicate Piece от 1-hop соседей),
но **соседи S друг друга PRUNE'ят** — у второй ноды A в её eager остаётся только тот
один сосед, от которого она получает body. Эффективно S по-прежнему шлёт всем 12, но
дальше каждый шлёт только дальше по single-parent tree → traffic ~1× после warmup.

### Выводы

- **Same-source: plumtree uncapped — победитель** (1.1× traffic, p50=110 ms на 100KB).
  Mesh сходится к fastest-path-tree из источника и держится.
- **Rotating source: plumtree-cap=10 ≈ prod-fec по latency** (70 ms p50), но
  **−25 % трафика** (9.8× vs 13.2×). Без cap'a mesh oscillates (1.7× но p50=244 ms).
- **plumtree-cap=5 — Pareto sweet spot** rotating: 5.1×, p50=83 ms.
- **На 1MB prod-fec выигрывает** (135 vs 208 ms у cap=10): FEC chunks (768B) идут
  параллельно, plumtree шлёт **whole body на каждом hop** — `1MB / 100MB/s = 10 ms`
  per hop × ~5 hops = +50 ms к сетевому времени.
- **pull-K=10**: дешёвый минимум 1.0×, но RTT-per-hop → p50=149-299 ms.
- **subscribe-prune**: 1.9× rotating / 1.1× same-source, p50 заметно хуже plumtree-cap.
  Subscribe-механика не даёт преимуществ.

Когда какой использовать:
- **Один лидер** (например, mempool коллектор) → plumtree uncapped: дёшево + быстро.
- **Много ротирующихся publisher'ов** (валидаторы) → plumtree-cap (5-10).
- **Крупный body (1 MB+)** → FEC chunks обязательны.

Следующий шаг — **plumtree + FEC chunks** (через `Spec.piece_count > 1`): сохранить
mesh-преимущество plumtree + параллелизм FEC для крупных body.

## Шаг 7. Optimum-P2P (RLNC) — теоретический потолок

`optimum-p2p` — push-based broadcast поверх **Random Linear Network Coding**: тело
бьётся на `k` source-symbol'ов, каждый узел при пересылке генерирует **новую
случайную линейную комбинацию** этих symbol'ов (в GF(256)), получатель собирает
любые `k` линейно-независимых комбинаций и инвертирует матрицу коэффициентов
обратно в тело. С идеальной топологией и совершенной координацией это
теоретический минимум трафика — каждый байт каждого peer'а несёт максимум
информации.

На mainnet (1 MB, 1124 ноды, 100 MB/s, full-decode-before-forward,
piece_peer_limit=1) bsim показывает **1.0× honest traffic** и p95=163 ms — то есть
ровно `body × honest_count` байт на проводе. Используем как **ceiling** в HTML-
отчёте: ни один практичный алгоритм не должен опуститься ниже.

### Почему RLNC не применим у нас

- **Coding cost**: каждый forwarder должен на лету решать систему `k × k` в
  GF(256) для декода + генерировать новую линейную комбинацию для каждого
  outbound piece. При `k=256` (1 MB / 4 KB) это сотни MB/s CPU-нагрузки на узел.
  На validator-grade железе ещё терпимо, но overhead не нулевой.
- **Coefficient overhead**: каждый piece несёт вектор из `k` GF(256)-коэффициентов
  (~256 B на piece при k=256). Для маленьких symbol'ов это +6 % wire overhead.
- **Full-decode-before-forward** даёт оптимум, но обнуляет основное преимущество
  RLNC (synthesis без декода). А с partial-decode (`forward_threshold=1`)
  получаем 3.4× amp из-за «синтетического шума» — forwarder'ы плодят linearly-
  dependent комбинации друг с другом.
- **Patent/lib status**: production-grade RLNC реализации (Kodo, Steinwurf) под
  commercial license; open-source альтернативы (jerasure) — Reed-Solomon, не
  RLNC. Писать своё — отдельная работа.
- **Cross-overlay dedup**: RLNC ломает hash-based dedup (каждая комбинация имеет
  уникальный hash), что несовместимо с нашим cross-overlay piece-level дедупом
  через chunk-hash.

**Вывод**: optimum-p2p оставляем как **theoretical reference** в каталоге —
сравниваем с ним practical алгоритмы (gossip-mask-fec, prod-fec, plumtree). Сам
не deploy'им.
